# Codex × Claude 协作规范 V2.3

状态：现行规范（2026-10-19 起生效，取代 V2.2 试行方案）｜维护：Claude（规划维护者）｜审阅：Codex｜批准：用户

本规范由 HUD-001 人工试点（[archive/HUD-001](archive/HUD-001/README.md)）、V2.2 试行方案（[plan_v2.md](plan_v2.md)，现已并入）与阶段 1 复盘三方意见合并而成。目标是：**保留安全边界，按风险分级控制流程成本，并让两个 Agent 在开发中能真正互相优化、和用户一起探讨方案。**

## 1. 原则

1. **用户是唯一决策者。** 范围、优先级、任务批准、方案选择、跨职责接口、合并 master 都由用户决定；Agent 之间的分歧交用户裁决。
2. **仓库是唯一沟通渠道，用户转话。** 两个 Agent 不直接通信，也不互相调用 CLI。交接写进 `codexandclaude/` 并提交到 Git；一方在会话结尾给出可直接粘贴的转话，由用户转给另一方。转话同时让用户了解双方在做什么，予以保留。
3. **一人写，一人审。** 每个任务只有一个实现者，由另一方独立审查；任何一方都不能审查自己的实现后直接集成。同一文件同一时间只属于一个任务。
4. **流程按风险分级。** 级别由改动风险决定，行数只作参考。
5. **规格优先于代码。** 用户已确认的规格是权威；代码与规格冲突时报告给用户，不反向改规格来解释代码。
6. **鼓励探讨与相互优化。** 两个 Agent 都可以对用户需求、对方方案与代码提出不同看法或优化建议，但必须附理由，最终由用户决定。UI 与交互设计以探索为先，规格是依据而不是束缚。
7. **冻结范围不变。** T0–T8 冻结范围保持不变，不擅自增加角色、系统、正式美术或玩法；冲突与缺口报告给用户裁决。根目录 Agents.md 的要求继续有效：每次改动必须编写或更新相关测试，交付前相关测试和验证全部通过，并创建对应 Git commit。

## 2. 角色

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 用户 | 定优先级、批准任务、选择方案、裁决分歧、实机验收、授权合并、在两方之间转话 | 抄写长段任务或结果 |
| Claude | 默认规划维护（任务板、待办清单、任务卡起草）；策划文档（Words/）；视觉呈现、Godot UI、交互反馈及其测试；审查 Codex 的实现 | 擅自合并；修改未分配给自己的文件 |
| Codex | 玩法、状态、数据、存档逻辑及其测试；验证流水线与工具；审查 Claude 的实现；默认执行集成与合并后回归 | 擅自扩大任务范围；跳过审查直接集成 |

- **“默认”只是执行职责，不是决定权。** 双方都可以提出任务；经用户授权，双方都可以承担规划维护或集成。
- 职责按任务卡写明的文件清单落地，而不是按目录名猜。UI 不一定都在 `game/ui/`，先调查实际代码归属，不因职责划分批量迁移现有实现。
- 跨职责改动（公共接口、`project.godot`、输入映射、存档格式）必须在任务卡里写明接口与影响，由用户批准。

## 3. 任务类型与分级

### 3.1 正式任务的级别

| 级别 | 适用 | 交接物 |
| --- | --- | --- |
| S 小 | 同时满足：单一职责；改动集中在少数文件；不碰公共接口、存档格式、输入映射、验证流水线或游戏逻辑；只需 G3 或单个专项测试即可证明 | 一份简版 `task.md`：目标、文件、检查；实现者在文末追加“交付”段，审查者追加“审查”段 |
| M 中 | 一般功能、缺陷修复、工具任务、文档改写 | `task.md` + `delivery.md` + `review.md` |
| L 大 | 跨职责，或改存档格式、公共接口、多个 Room 或系统 | M 的全部 + 接口约定 + 用户实机验收记录 |

无论哪一级，**批准依据、修改范围、测试结果和审查结论都必须留在 Git 记录里**。拿不准时按高一级处理；进行中发现风险变大，实现者停止并说明，由用户决定升级或拆分。

### 3.2 方案探讨

功能类任务（玩法、UI、交互、系统设计）在写任务卡之前，先做方案探讨：

1. 起草方在 `codexandclaude/proposals/<ID>.md` 写出：要解决的问题、2～3 个可选方案及各自的取舍、需要用户回答的疑问。提案不放在 `tasks/` 下，因为 `tasks/<ID>/` 只用于已有任务卡并登记在任务板上的任务。
2. 另一方补充意见：同意、反对、改进或新方案，附理由。
3. 用户拍板，结论写入任务卡“依据”；立项时把提案随任务卡一并移入 `tasks/<ID>/proposal.md`。未被采纳的提案标明结论后留在 `proposals/` 作记录。

小的缺陷修复、文档改写和工具任务默认可以跳过方案探讨，跳过的是强制的 2～3 个方案与双边讨论，不禁止主动探讨。工具任务若影响跨职责接口或存在重大取舍，按风险升级或提出探讨，不能借“工具任务”扩大已批准范围。

### 3.3 探索型任务（UI 与交互优先）

UI 与交互开发先走探索型任务，再进入正式实现：

- 产出 2～3 个**可以实际看、实际操作**的方案（游戏内预览场景或可交互的页面原型），而不是只给文字描述。
- 原型放在独立位置，可以随时丢弃：Godot 原型只新增 `game/prototypes/<ID>/` 下的场景与脚本，用 `--path game <预览场景>` 直接启动，可以读取正式资源，但不得修改正式主场景、共享脚本、`project.godot` 或正式存档；网页原型放在 `codexandclaude/prototypes/<ID>/`。
- 原型不跑正式任务的全套门禁，但仍按 Agents.md 补充能证明“可启动、可演示”的最小测试并提交。
- 小的 UI 缺陷修复不必走整套原型；新增或明显改变交互方案时默认先探索。
- T7 与其他规格是依据，不是束缚。方案可以偏离规格，但须标出偏离点与理由；用户选中偏离方案后，在正式任务中同步修订对应规格。
- 用户挑选、组合或要求再探索；只有选中的方案才转为正式任务，按 3.1 的级别审查与合并。

## 4. 目录与状态

```text
codexandclaude/
  README.md          入口
  collaboration.md   本规范
  env.md             检查入口与本机环境细节
  BOARD.md           任务板：已立项任务的汇总
  BACKLOG.md         待办清单：尚未立项的事项
  proposals/<ID>.md  方案探讨中的提案（立项前；立项时移入任务目录）
  tasks/<任务ID>/    task.md，以及 proposal.md、delivery.md、review.md、acceptance.md、integration.md
  prototypes/<ID>/   网页形式的探索原型（Godot 原型在 game/prototypes/<ID>/）
  tools/             协作工具
  archive/           已完成并归档的任务
  worktrees/         （git 忽略）各自的工作区
  runs/              （git 忽略）原始日志
```

任务 ID 用 `领域-序号`：`DOC`、`UI`、`SYS`、`SAVE`、`ENV`、`BUG`、`EXP`（探索型）。

- **每个任务的权威状态写在它自己的 `task.md` 首部**，由当前持有任务的一方更新。状态：`草稿 → 待批准 → 进行中 → 待审查 → 待验收 → 待合并 → 已完成`，另有 `阻塞`、`已取消`。
- **BOARD.md 与 BACKLOG.md 由规划维护者串行更新。** 任务关闭后统一刷新，并在表头注明汇总所依据的 master SHA；并行任务不碰这两个文件。

## 5. 单个任务的生命周期

1. **提案**：任何一方都可以提出任务；功能类任务先做方案探讨（3.2），UI 与交互先做探索（3.3）。
2. **起草与批准**：规划维护者写 `task.md`，用户批准（可以是会话中的明确回复，卡中记录原话要点与日期）。
3. **任务卡入库**：
   - M/L 级默认规划先行：任务卡经规划分支合入 master 后再开工。
   - 已批准、互不冲突的多张任务卡可以**批量合入**一次。
   - S 级，或用户在会话中批准要点的任务，任务卡可以与实现放在同一分支，卡中写明批准依据。
4. **实现**：实现者在自己的 worktree、从最新 master 新建分支 `<agent>/<ID>`；先复现或先写失败测试，再修改；按第 7 节检查后提交实现，得到**实现 SHA**。随后单独提交交付记录（写明实现 SHA、检查汇总、未验证项与用户验收步骤），得到**交付 SHA**。交接时两个 SHA 都要给出。
5. **审查**：审查者在自己的 worktree 用 `git switch --detach <交付SHA>` 固定，先确认 `git diff <实现SHA> <交付SHA>` 只有记录文件变化，再按第 8 节审查；从交付 SHA 建立 `<审查者>/<ID>-review`，提交审查记录，得到**审查 SHA**。结论：`通过` / `需修改` / `需用户裁决`。同一问题来回修改不超过两轮，第三轮交用户裁决。需修改时，实现者先把分支快进到审查 SHA 再修订，保留审查历史。
6. **验收（G4）**：涉及手感、画面、输入、UI 的任务，审查通过后由用户实机检查，**G4 通过是合并的前提**。**验收入口在任务卡阶段就要规划**：写明如何直达验收状态、如何隔离存档、用户检查什么；入口与实现一并交付，不在审查后另起任务。
7. **合并**：用户授权后，集成者合并**审查 SHA**（不合并可移动的分支名）。审查后实现分支上出现的任何代码变化，都必须重新检查、重新审查。合并后按矩阵在 master 检查，结果另作证据提交。
8. **失败处理**：合并后检查失败时，暂停后续所有集成，保留失败日志，先区分代码失败与环境故障；撤销用 `git revert` 或经用户批准的修复，不用 reset 改写历史。
9. **收尾与归档**：集成者在 master 提交集成记录并把任务卡状态改为已完成；规划维护者随后刷新 BOARD、BACKLOG。每完成 3～5 个任务归档一次。

用户转话的固定要素：任务 ID、相关 SHA（基线、实现、交付、审查）、分支、要检查的重点、停止条件。

## 6. 任务卡模板

```markdown
# <ID>：<标题>

状态：草稿｜级别：S/M/L｜实现：Claude/Codex｜审查：另一方
工作区：worktrees/<agent>｜基线：master@<完整SHA>｜依赖：<任务ID 或 无>

## 目标
## 依据（规格章节；用户决定的日期与原话要点；方案探讨结论）
## 允许修改的文件
## 接口与影响（L 级或跨职责时必填）
## 完成标准
## 检查（按第 7 节矩阵）
## 验收入口（涉及 G4 时必填：直达方式、存档隔离、用户检查项）
## 回滚方案
## 不在范围内
```

交付记录写：被测实现 SHA、实际修改的文件、复现前后证据、第 7 节要求的检查证据、未验证项、用户验收步骤。审查记录写：被审 SHA、结论、复跑的检查证据、问题清单与优化建议。两者都不记录自身所在提交的哈希。

## 7. 质量门与检查矩阵

| 门 | 内容 |
| --- | --- |
| G1 专项 | 本任务新增或相关的 Godot / Python 测试 |
| G2 引擎全量 | `scripts/verify_game.py` 全部套件 |
| G3 Python | `tests/` 与 `codexandclaude/tests/` 全部 |
| G4 实机 | 用户按验收步骤检查画面、输入、手感 |

| 改动类型 | 实现者提交前 | 审查通过后、合并前 | 集成者合并后（master） |
| --- | --- | --- | --- |
| 游戏代码、输入、存档、公共接口 | G1 + G2 + G3 | 涉及 UI/操作时 G4 | G2 + G3 |
| 验证流水线与协作工具 | G1 + G2 + G3 | — | G2 + G3 |
| 只在验收进程内运行的验收脚本（不改 game/ 与验证流水线） | 脚本自测 + G3 | — | G3 |
| 纯文档、归档、链接调整 | G3 | — | G3 |
| 探索型原型（不合并正式代码） | 能启动、能演示 | 用户挑选 | 不合并或按选中后的正式任务处理 |
| 只追加证据记录 | G3 | — | 不重新触发 G2 |

**通过条件**：退出码为 0、预期套件全部执行、汇总行与登记一致且 failures=0、日志中没有错误、解析失败、泄漏或超时。由 `scripts/verify_game.py` 与 `codexandclaude/tools/run_checks.py` 判定。

**入库证据（交付与审查记录的必填项）**：原始日志放 `runs/`（不入库），以下内容必须写进交付或审查记录并提交，换一台机器也能核对：

- 被测 SHA，以及工作区是否有未提交改动；先验证再提交时，说明被测文件与提交内容的对应关系；
- 工具版本；
- 实际执行的命令；
- 套件完整性与各项计数（预期与实际条目数、通过数）；
- 失败时，原有失败与新引入失败分开报告。

可以直接摘录 `run_checks.py` 生成的汇总（字段说明见 [env.md](env.md)），不必逐项手抄；但不能只写“已通过”。

## 8. 审查要求

审查同时覆盖三方面：

1. **正确性**：范围是否符合任务卡；完成标准逐条核对；对照规格检查行为；独立复跑规定的检查。
2. **变异检查**：对关键修复或规则，审查者在自己的工作区临时把实现改回错误或改变边界（例如把“严格低于”改成“低于或等于”），确认相关测试会失败；检查后立即还原。结果写入审查记录。
3. **优化建议**：可读性、结构、性能、复用、测试质量等方面的改进。优化建议不阻断合并，标为非阻断；实现者可当场采纳，或由规划维护者记入待办清单。当场采纳并改了代码的，按第 5 节第 7 步重新检查、重新审查。双方都可以对对方的代码主动提出重构建议。

## 9. Git 与工作区

- **主目录 `D:\31days` 属于用户。** Agent 在各自的 `worktrees/claude`、`worktrees/codex` 中工作；源码与测试改动一律在工作区完成。例外：集成者可以在 master 上直接提交合并、集成记录与任务卡状态更新。集成时如待合并文件与用户未提交的改动重叠，立即停止并报告。
- **保护现有工作。** 操作前查看 Git 状态与差异；现有未提交变更必须保留，不自动暂存、提交、覆盖、清理或回滚他人工作。新建 worktree 以明确提交为基线，主目录未提交内容不会自动进入新 worktree，用户确认前不复制到分支。
- 分支命名：实现 `<agent>/<ID>`，审查 `<审查者>/<ID>-review`，规划 `plan/<ID>`。审查一律用 detached HEAD 固定 SHA。
- 提交只用显式文件列表暂存，不用 `git add -A`；提交信息首行带任务 ID。多行、含引号或特殊字符的提交说明用 `git commit -F <文件>`，细节见 [env.md](env.md)。
- 只读审查没有文件改动时，不创建空提交。
- 不推送远程、不改全局 Git 配置、不删除对方的分支或工作区。

## 10. 文档规则

- **Words/ 是现行规格。** 修订直接改进正文对应章节，过时表述删除。每份规格文档末尾保留变更记录表，每行写明日期、改了什么、来源（谁确认、出处）。T2～T5.4 在改写为现行版时补建该表（待办清单 BL-022～BL-025），在此之前其历次修订保留在原文中，不得删除。
- **同一条规则只在一份主文档中完整描述，其他文档只放链接。**
- **规格与代码冲突时，报告给用户裁决。**
- **game/docs/ 是实施记录。** 测试数量、帧数、存档字段名、场景路径写在这里，不写进 Words/。
- **待决事项集中管理。** `Words/待决事项总表.md` 收录待决事项；用户裁决后，结论写入对应主文档，总表中的条目改为已裁决并在裁决记录中写明日期、结论、来源链接，不直接删除。
- **尚未立项的事项记入 BACKLOG.md，** 不散落在各任务记录里。

## 11. 人工执行与许可

- 当前仅人工触发：用户在两个官方客户端分别下达任务、确认必要操作、转交结果。
- Claude 保留手动审批；不得自行启用自动授权、跳过权限、后台循环或调用另一个 Agent。
- 不提取、复制或互传订阅令牌，不配置非官方代理，不规避任何一方的地区、账户或用量限制。
- CLI 自动化需先核对两家服务条款与计费，经用户批准后另行讨论（见待办清单）。
- 不自行安装依赖、推送远程、发布、删除工作区或修改全局 Git/账号配置。
- 不自动合并或推送；合并须用户授权。
