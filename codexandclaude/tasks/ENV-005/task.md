# ENV-005：检查证据自动汇总

状态：已完成（2026-10-20 Claude复审通过，用户授权合入master；G2复用及G3重跑见integration.md）｜级别：M（工具）｜实现：Codex｜审查：Claude
工作区：worktrees/codex｜基线：本任务卡合入后的 master 最新提交（实现者在交付记录中写明完整 SHA）｜依赖：无

## 目标

完成待办 BL-104：让检查入口自动生成可直接贴进交付与审查记录的证据摘要，并明确“何时可以复用同一内容的测试证据”，减少两边手抄 SHA、计数、哈希以及为纯记录提交重跑 G3 的重复劳动。缺少最终汇总的运行仍不算通过。

## 依据

- 待办 BL-104（Codex 阶段复盘意见）；协作规范 V2.3 中交付与审查的必填证据字段（被测 SHA、是否干净、工具版本、命令、完整性与计数、新旧失败）。
- 路线图第 5 节第二批建议。

## 现状（起草时核对 master@07cb0cc）

`codexandclaude/tools/run_checks.py` 的 `summary.json` 已记录：被测 SHA、`dirty`、`git status` 文件列表、工具路径与版本、逐命令日志及其 SHA256、G2 报告 SHA256、各关卡执行数与是否完整。目前缺：

1. 一段可直接粘贴的中文证据摘要（交付和审查记录现在都靠人工从 JSON 抄写，本次会话里多次出现抄写或计数口径问题）。
2. 工作区不干净时，已跟踪改动与未跟踪文件的**内容**哈希；目前只有文件名，无法事后证明“测的就是这份内容”。
3. 被测内容的稳定指纹，以及据此判断证据可否复用的规则：例如实现提交与只改了交付记录的交付提交，代码树相同，G2 证据理应可以复用。

## 要求

1. 每次运行在 `summary.json` 同目录生成 `evidence.md`：被测 SHA、是否干净、模式与命令、工具版本、各关卡执行数/预期数/是否完整/是否通过、失败清单（区分旧失败与新失败时给出依据）、日志与报告哈希、开始与结束时间。格式固定，可整段贴进 `delivery.md` 或 `review.md`。
2. 不干净时，记录已跟踪改动的 diff 哈希和每个未跟踪文件的内容哈希；摘要中醒目标注“非干净运行”。
3. 记录被测内容指纹：至少包括提交的树哈希；并能按路径范围（例如排除 `codexandclaude/tasks/`、`codexandclaude/runs/` 等纯记录路径）给出“代码与测试内容”指纹。
4. 提供复用判断：给定两次提交（或一次已有运行的摘要与当前提交），输出两者在指定范围内内容是否相同、哪些路径不同，以及据此“可复用 / 不可复用”的结论与理由。复用规则写进 `env.md`；规则须保守：任何非记录路径不同都不可复用，不干净的运行不能作为复用来源。
5. 任何一关未完成或未生成最终汇总，摘要明确写“不通过”，不得输出看似通过的摘要。
6. 现有命令行用法与 `summary.json` 已有字段保持兼容，不删字段；`full`、`focused`、`env` 三种模式都生成摘要。

## 允许修改的文件

- `codexandclaude/tests/test_run_checks.py` 及必要的新测试文件。
- `codexandclaude/env.md`：摘要用法与复用规则。
- `codexandclaude/collaboration.md`：仅在需要把“可用摘要代替手写证据字段”写入交付/审查要求时，改相关一两句；不改其他规则。
- `codexandclaude/tasks/ENV-005/task.md`（只更新首部状态）、`delivery.md`（新增）。

## 完成标准

1. 满足要求 1～6，各有自动测试（可用临时 Git 仓库或模拟 runner）。
2. 用本任务自己的交付演示：交付记录中的证据段落由工具生成；并演示“实现提交 → 只改记录的交付提交”判定为可复用、“改了任意代码文件”判定为不可复用。
3. 变异检查（实现者自测，审查者复现）：让某关少执行一项、让最终汇总缺失、让不干净运行作为复用来源、让非记录路径不同，均得到“不通过”或“不可复用”。
4. G3 通过；工具本身不改游戏代码，G2 只需跑一次以证明 full 模式摘要正确。
