# Codex × Claude 协作方案 V2（提案）

状态：提案，待用户确认、Codex 审阅后生效｜起草：Claude｜日期：2026-10-19

本方案在 HUD-001 试点（见 [integration.md](integration.md)）基础上修订。试点证明了独立工作区、先复现后修复、交叉审查和人工验收是有效的；同时暴露出流程文档过重、合并后未全量回归、证据不入库、环境路径写死等问题。V2 的目标是：**保留安全边界，把单个任务的流程成本降到“一张任务卡 + 一次交付 + 一次审查”。**

生效前 [collaboration.md](collaboration.md) 仍是现行规范；V2 确认后合并进 collaboration.md 并在此文件标注“已并入”。

## 1. 原则

1. **用户是唯一决策者。** 范围、优先级、跨职责接口、合并 master 都由用户批准；Agent 之间的意见分歧交用户裁决。
2. **仓库是唯一沟通渠道。** 两个 Agent 不直接通信，也不互相调用 CLI。所有交接写进 `codexandclaude/` 的文件并提交到 Git；用户只需转一句话。
3. **一人写，一人审。** 每个任务只有一个实现者；另一方做独立审查。同一文件同一时间只属于一个任务。
4. **流程按任务大小分级。** 小改动不写长文档，大改动才走全流程。
5. **冻结范围不变。** T0–T8 范围、Agents.md 的“每次改动必须测试 + 提交”继续有效。

## 2. 角色

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 用户 | 定优先级、批准任务卡、裁决分歧、实机验收、授权合并、在两个客户端之间转一句话 | 抄写长段任务或结果 |
| Claude（规划牵头） | 维护任务板（第 4 节）、起草任务卡；策划文档（Words/）现行化与一致性；视觉呈现、Godot UI、交互反馈及其测试；审查 Codex 的提交 | 擅自合并 master；修改未分配给自己的文件 |
| Codex（系统与集成） | 玩法、状态、数据、存档逻辑及其测试；维护 `scripts/verify_game.py` 等验证流水线；审查 Claude 的提交；用户授权后执行合并与合并后全量回归 | 擅自扩大任务范围；跳过审查直接合并 |

职责按“任务卡写明的文件清单”落地，而不是按目录名猜。跨职责的改动（公共接口、`project.godot`、输入映射、存档格式）必须在任务卡里写明接口和影响，并由用户批准。

## 3. 任务分级

| 级别 | 适用 | 交接物 | 审查 |
| --- | --- | --- | --- |
| S 小 | 单一职责、约 50 行以内、不碰公共接口/存档/输入配置 | 只需任务板一行 + 提交说明 | 审查者在会话中给结论，不写文件 |
| M 中 | 一般功能或缺陷修复 | `task.md` + `delivery.md` + `review.md` | 独立复跑测试并写 `review.md` |
| L 大 | 跨职责、改存档格式/公共接口、多个 Room 或系统 | M 的全部 + 任务卡中的接口约定 + 用户实机验收记录 | 同 M，另需合并后全量回归记录 |

拿不准时按高一级处理。任务进行中发现规模变大，实现者停止并在 `delivery.md` 里说明，由用户决定升级或拆分。

## 4. 任务板与目录结构

```text
codexandclaude/
  README.md          入口：只放现行规则与链接
  collaboration.md   现行协作规范
  BOARD.md           任务板：一张表，每个任务一行
  env.md             本机工具路径与统一检查命令
  tasks/
    <任务ID>/
      task.md        任务卡（规划者起草，用户批准）
      delivery.md    实现者交付记录
      review.md      审查者结论
  archive/           已完成任务整体移入，例如 archive/HUD-001/
  worktrees/         （git 忽略）各自的工作区
  runs/              （git 忽略）原始日志
```

任务 ID 用 `领域-序号`：`DOC-001`（策划文档）、`UI-001`、`SYS-001`（玩法/系统）、`SAVE-001`、`ENV-001`（工具与流程）、`BUG-001`。

BOARD.md 只有一张表：

| ID | 级别 | 标题 | 实现 | 审查 | 状态 | 分支 |
| --- | --- | --- | --- | --- | --- | --- |
| DOC-001 | M | T0/T1 现行化 | Claude | Codex | 待批准 | claude/DOC-001 |

状态只用这几个：`草稿 → 待批准 → 进行中 → 待审查 → 待验收 → 待合并 → 已完成`，另有 `阻塞` 和 `已取消`。状态由当前持有任务的一方在自己的提交中更新。

## 5. 单个任务的生命周期

1. **起草**：Claude 在 `tasks/<ID>/task.md` 写任务卡（模板见第 6 节），BOARD 状态记“待批准”。系统类任务可以由 Codex 起草，格式相同。
2. **批准**：用户看任务卡，回复“批准”或修改意见。
3. **实现**：实现者在自己的 worktree、从最新 master 新建分支 `<agent>/<ID>`；先复现或先写失败测试，再修改；跑完第 7 节的检查后提交，写 `delivery.md`，BOARD 改为“待审查”。
4. **审查**：审查者在自己的 worktree 检出该分支，独立复跑检查，写 `review.md`，结论只有三种：`通过` / `需修改`（列出具体问题） / `需用户裁决`（双方观点各一段）。同一问题来回修改不超过两轮，第三轮直接交用户裁决。
5. **验收**：涉及手感、画面、输入、UI 的任务，用户按 `delivery.md` 中的验收步骤实机检查。
6. **合并**：用户说“合并”后，Codex 把分支合入 master，在 master 上跑**全量**回归（第 7 节 G2+G3），结果补进 `review.md` 末尾，BOARD 改为“已完成”。全量回归失败则回退合并、重新打开任务。
7. **归档**：每完成 3～5 个任务，Claude 把已完成任务目录移到 `archive/`，保持 README 和 BOARD 简短。

### 用户需要转的话（固定句式）

用户不需要复制任务内容，只转一句：

- 给实现者：`执行 codexandclaude/tasks/UI-002/task.md`
- 给审查者：`审查 UI-002，分支 claude/UI-002`
- 回给实现者：`UI-002 审查结果在 review.md，按意见修改`
- 给集成者：`UI-002 验收通过，合并`

## 6. 任务卡模板

```markdown
# <ID>：<标题>

级别：S/M/L｜实现：Claude/Codex｜审查：另一方｜基线：master@<短哈希>

## 目标
一两句话说明要解决的问题和完成后的可见结果。

## 依据
Words/ 或 game/docs/ 中的具体章节；用户在会话中的决定（注明日期）。

## 允许修改的文件
- 路径（新增的标注“新增”）

## 接口与影响（仅 L 级或跨职责时填写）
公开方法、信号、存档字段、输入映射的变化，以及谁会受影响。

## 完成标准
- 可验证的条目；先复现的问题写明复现方式。

## 检查
专项测试命令；是否需要用户实机验收及验收步骤。

## 不在范围内
明确列出容易顺手扩大的内容。
```

`delivery.md` 只写：实际修改的文件、复现前后证据、检查命令与通过计数、未验证项、提交哈希。`review.md` 只写：结论、复跑结果、问题清单（文件:行号）、合并后回归结果。

## 7. 质量门

| 门 | 内容 | 谁、何时 |
| --- | --- | --- |
| G1 专项 | 本任务新增或相关的 Godot / Python 测试 | 实现者提交前 |
| G2 引擎全量 | `scripts/verify_game.py` 全部套件，零失败、零解析错误、零泄漏、零超时 | 实现者提交前；集成者合并后在 master 再跑 |
| G3 Python | `tests/` 与 `codexandclaude/tests/` 全部通过 | 同 G2 |
| G4 实机 | 用户按验收步骤检查画面、输入、手感 | 用户，涉及 UI/操作的任务 |

通过的标准是看测试汇总里的真实计数，不是看进程退出码。原有失败与新引入失败分开报告。原始日志放 `runs/`（不入库），**汇总计数和关键结论必须写进 `delivery.md` / `review.md` 入库**，换一台机器也能核对。

## 8. Git 与工作区

- **主目录 `D:\31days` 只属于用户。** 两个 Agent 都不在主目录写代码；集成者合并时只做快进或合并提交，不碰用户的未提交文件。
- **每个 Agent 一个长期工作区：** `worktrees/claude`、`worktrees/codex`。每个任务开始时从最新 master 新建分支 `<agent>/<ID>`，任务结束后分支可删，工作区保留。
- 提交只用显式文件列表暂存，不用 `git add -A`；提交信息首行带任务 ID，例如 `fix(ui): UI-002 ...`。
- 不推送远程、不改全局 Git 配置、不删除对方的分支或工作区。
- `.git` 所有权问题：仓库目前属于 Codex 的沙盒用户，Claude 这边每次用 `git -c safe.directory=D:/31days` 临时放行，不修改全局配置；如用户希望一劳永逸，由用户自己执行全局 `safe.directory`。

## 9. 文档规则

- **Words/ 是“现行规格”**：修订直接改进正文对应章节，过时表述删除；每份文档末尾保留一张变更记录表（日期、改了什么、链接）。同一条规则只在一份主文档中完整描述，其他文档只放链接。
- **game/docs/ 是实施记录**：测试数量、帧数、存档字段名、场景路径写在这里，不写进 Words/。
- **待决事项集中管理**：Words/ 新增一页待决事项总表，取代散落各文档的“待明确”小节；用户裁决后从表中移除并写入对应主文档。
- 策划文档的改写由 Claude 实现、Codex 审查（重点核对与已实现代码是否一致）。

## 10. 启动步骤

**阶段 0：整理（1～2 个 S/M 任务）**

- `ENV-001`（Codex 实现，Claude 审查）：新增 `env.md` 和一个统一检查脚本（例如 `scripts/run_checks.ps1`，依次执行 G1/G2/G3），替换任务卡中写死的 Godot 与 Python 绝对路径。
- `ENV-002`（Claude 实现，Codex 审查）：建立 `BOARD.md`、`tasks/`、`archive/`，把 HUD-001 的试点文件移入 `archive/HUD-001/`，README 精简为现行入口，同步更新 `tests/test_collaboration.py`。
- 用户自行处理主目录的未提交改动（两份 xlsx 和 `game/project.godot`）：提交、另存或还原。这样合并时不再需要备份和恢复的绕行操作。

**阶段 1：试运行（2～3 个任务）**

- `DOC-001`（Claude 实现，Codex 审查）：T0、T1 改写为现行版 + 变更记录表，同步 `tests/test_planning_documents.py`。
- `DOC-002`（Claude 实现，Codex 审查）：建立待决事项总表（剧情奖励 +10 与补满的结算、残存可能性实体、普通帮助 +4 能否重复、货币去留、日期地形变体、换怪规则等），交用户逐项裁决。
- 一个由 Codex 实现、Claude 审查的系统类任务，从用户裁决的待决事项中选取，验证反方向的流程。

**阶段 2：复盘**

试运行结束后，用户与双方各写几条“哪里慢、哪里多余”，修订本方案并并入 collaboration.md。是否引入 CLI 自动调用另行讨论，需先核对两家服务条款与计费，且仍保留用户审批。

## 11. 不做的事

- 不让两个 Agent 自动互相调用、后台循环或在无人审批时合并。
- 不共享或转移任何账号令牌，不使用非官方代理。
- 不因为协作方案而扩大 T0–T8 冻结范围。
