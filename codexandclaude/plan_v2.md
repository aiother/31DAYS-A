# Codex × Claude 协作方案 V2（提案）

状态：提案 V2.2，已吸收 Codex 两轮审阅意见，待用户确认后试行｜起草：Claude｜审阅：Codex｜日期：2026-10-19

本方案在 HUD-001 试点（见 [integration.md](integration.md)）基础上修订。试点证明了独立工作区、先复现后修复、交叉审查和人工验收是有效的；同时暴露出流程文档过重、合并后未全量回归、证据不入库、环境路径写死等问题。V2 的目标是：**保留安全边界，按风险分级控制每个任务的流程成本。**

**生效方式**：用户确认前，[collaboration.md](collaboration.md) 是现行规范。用户确认后按本方案试行；试行期间与 collaboration.md 冲突时，以用户批准的本方案为准。阶段 2 复盘修订后，再正式并入 collaboration.md，并在此文件标注“已并入”。

## 1. 原则

1. **用户是唯一决策者。** 范围、优先级、任务批准、跨职责接口、合并 master 都由用户决定；Agent 之间的分歧交用户裁决。
2. **仓库是唯一沟通渠道。** 两个 Agent 不直接通信，也不互相调用 CLI。所有交接写进 `codexandclaude/` 并提交到 Git；用户只需转一句话。
3. **一人写，一人审。** 每个任务只有一个实现者，由另一方独立审查。任何一方都不能审查自己的实现后直接集成。同一文件同一时间只属于一个任务。
4. **流程按风险分级。** 级别由改动的风险决定，行数只作参考。
5. **规格优先于代码。** 用户已确认的规格是权威；代码与规格冲突时报告给用户，不反向改规格来解释代码。
6. **冻结范围不变。** T0–T8 范围、Agents.md 的“每次改动必须测试 + 提交”继续有效。

## 2. 角色

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 用户 | 定优先级、批准任务、裁决分歧、实机验收、授权合并、在两个客户端之间转一句话 | 抄写长段任务或结果 |
| Claude | 默认规划维护：汇总任务板、起草任务卡；策划文档（Words/）现行化；视觉呈现、Godot UI、交互反馈及其测试；审查 Codex 的实现 | 擅自合并；修改未分配给自己的文件 |
| Codex | 玩法、状态、数据、存档逻辑及其测试；维护验证流水线；审查 Claude 的实现；默认执行集成与合并后回归 | 擅自扩大任务范围；跳过审查直接集成 |

- **“默认”只是执行职责，不是决定权。** 双方都可以提出任务提案；规划维护不等于决定做什么，集成执行不等于对另一方有指挥权。经用户授权，双方都可以承担规划维护或集成。
- 职责按任务卡写明的文件清单落地，而不是按目录名猜。跨职责的改动（公共接口、`project.godot`、输入映射、存档格式）必须在任务卡里写明接口和影响，并由用户批准。

## 3. 任务分级

| 级别 | 适用（风险判断，行数仅参考） | 交接物 |
| --- | --- | --- |
| S 小 | 单一职责，不碰公共接口、存档、输入配置或验证流水线 | 一份简版 `task.md`：目标、文件、检查；实现者在文末追加交付段，审查者追加结论段 |
| M 中 | 一般功能、缺陷修复、工具任务 | `task.md` + `delivery.md` + `review.md` |
| L 大 | 跨职责，或改存档格式、公共接口、多个 Room 或系统 | M 的全部 + 接口约定 + 用户实机验收记录 |

无论哪一级，**批准依据、修改范围、测试结果和审查结论都必须留在 Git 记录里**。S 只是把它们压缩进一个文件。拿不准时按高一级处理；进行中发现风险变大，实现者停止并说明，由用户决定升级或拆分。

## 4. 目录与任务状态

```text
codexandclaude/
  README.md          入口：只放现行规则与链接
  collaboration.md   现行协作规范
  BOARD.md           任务板汇总（只由规划维护者串行更新）
  tasks/<任务ID>/    task.md、delivery.md、review.md
  tools/             协作检查入口（ENV-001）
  archive/           已完成任务，例如 archive/HUD-001/
  worktrees/         （git 忽略）各自的工作区
  runs/              （git 忽略）原始日志
```

任务 ID 用 `领域-序号`：`DOC`（策划文档）、`UI`、`SYS`（玩法/系统）、`SAVE`、`ENV`（工具与流程）、`BUG`。

- **每个任务的状态写在它自己的 `task.md` 首部**，由当前持有任务的一方在任务分支里更新。状态只用：`草稿 → 待批准 → 进行中 → 待审查 → 待验收 → 待合并 → 已完成`，另有 `阻塞`、`已取消`。
- **BOARD.md 只是汇总**，并行任务不碰它；由规划维护者在单独的小提交里串行更新（以后可由工具从各 `task.md` 自动生成）。

## 5. 单个任务的生命周期

1. **提案与起草**：任何一方都可以提出任务。规划维护者（默认 Claude）在规划分支 `plan/<ID>` 上写 `task.md`，状态记“待批准”。
2. **批准**：用户看任务卡，回复“批准”或修改意见；批准后由集成者把规划提交合入 master，实现者从这个 master 出发。
3. **实现**：实现者在自己的 worktree、从最新 master 新建分支 `<agent>/<ID>`；先复现或先写失败测试，再修改；按第 7 节矩阵检查后提交实现，得到**实现 SHA**。随后单独提交交付记录（M/L 级为 `delivery.md`；S 级在 `task.md` 末尾追加“交付”段），其中写明实现 SHA 和用户验收步骤，得到**交付 SHA**。交接时两个 SHA 都要给出。
4. **审查**：审查者在自己的 worktree 用 `git switch --detach <交付SHA>` 固定到交付提交（不检出实现者正在占用的分支），先用 `git diff <实现SHA> <交付SHA>` 确认两者之间只有记录文件变化，再独立复跑检查。然后从交付 SHA 建立审查分支 `<审查者>/<ID>-review`，提交审查记录（M/L 级为 `review.md`；S 级在 `task.md` 末尾追加“审查”段），得到**审查 SHA**。审查分支建立在交付提交之上，S 级双方按先后追加同一文件，不会冲突。结论只有三种：`通过` / `需修改`（列出具体问题，带文件:行号） / `需用户裁决`（双方观点各一段）。同一问题来回修改不超过两轮，第三轮直接交用户裁决。
5. **验收（G4）**：审查通过后，涉及手感、画面、输入、UI 的任务由用户按交付记录中的验收步骤实机检查，验收通过是合并的前提。
6. **合并**：用户说“合并”后，集成者合并**审查 SHA**（它已包含实现、交付和审查记录），不合并可继续移动的分支名。审查之后实现分支上出现的任何代码变化，都必须重新检查、重新审查。合并后在 master 上按矩阵执行检查，结果另作证据提交。
7. **失败处理**：合并后检查失败时，**暂停后续所有集成**，保留失败日志，先区分是代码失败还是环境故障（工具缺失、路径、超时等）。需要撤销时用 `git revert` 生成明确的撤销提交，或经用户批准提交修复；不使用 reset 改写历史。
8. **归档**：每完成 3～5 个任务，规划维护者把已完成任务移到 `archive/`，保持 README 和 BOARD 简短。

### 用户需要转的话（固定句式）

- 给实现者：`执行 UI-002，任务卡 codexandclaude/tasks/UI-002/task.md（master@<SHA>）`
- 给审查者：`审查 UI-002，实现 SHA <完整SHA>，交付 SHA <完整SHA>`
- 回给实现者：`UI-002 需修改，意见在审查 SHA <完整SHA> 的审查记录`
- 给集成者：`UI-002 验收通过，合并审查 SHA <完整SHA>`

## 6. 任务卡模板

```markdown
# <ID>：<标题>

状态：草稿｜级别：S/M/L｜实现：Claude/Codex｜审查：另一方
工作区：worktrees/<agent>｜基线：master@<完整SHA>｜依赖：<任务ID 或 无>

## 目标
一两句话说明要解决的问题和完成后的可见结果。

## 依据
Words/ 或 game/docs/ 中的具体章节；用户在会话中的决定（注明日期和原话要点）。

## 允许修改的文件
- 路径（新增的标注“新增”）

## 接口与影响（L 级或跨职责时必填）
公开方法、信号、存档字段、输入映射的变化，以及谁会受影响。

## 完成标准
- 可验证的条目；先复现的问题写明复现方式。

## 检查
按第 7 节矩阵列出要跑的检查；是否需要用户实机验收及步骤。

## 回滚方案
出问题时撤销哪些提交、存档或配置是否需要兼容处理。

## 不在范围内
明确列出容易顺手扩大的内容。
```

交付记录只写：被测实现 SHA、实际修改的文件、复现前后证据、检查命令与汇总、未验证项、用户验收步骤。审查记录只写：被审实现 SHA 与交付 SHA、结论、复跑汇总、问题清单。**两者都不记录自身所在提交的哈希**，避免循环。M/L 级用独立的 `delivery.md`、`review.md`；S 级写成 `task.md` 末尾的“交付”“审查”两段，以下凡提到交付或审查记录，均按此适用。

## 7. 质量门与检查矩阵

| 门 | 内容 |
| --- | --- |
| G1 专项 | 本任务新增或相关的 Godot / Python 测试 |
| G2 引擎全量 | `scripts/verify_game.py` 全部套件 |
| G3 Python | `tests/` 与 `codexandclaude/tests/` 全部 |
| G4 实机 | 用户按验收步骤检查画面、输入、手感 |

| 改动类型 | 实现者提交前 | 审查通过后、合并前 | 集成者合并后（master） |
| --- | --- | --- | --- |
| 游戏代码、输入、存档、公共接口 | G1 + G2 + G3 | 涉及 UI/操作时 G4 | G2 + G3 |
| 验证流水线与协作工具 | G1 + G2 + G3 | — | G2 + G3 |
| 纯文档、归档、链接调整 | G3 | — | G3 |
| 只追加证据记录（交付 / 审查记录） | G3 | — | 不重新触发 G2 |

**通过条件**：进程退出码为 0、预期套件全部执行、每个套件的汇总行与登记一致且 failures=0、日志中没有错误、解析失败、泄漏或超时。现有 `scripts/verify_game.py` 已同时检查这些条件，直接复用，不另写判断逻辑。原有失败与新引入失败分开报告。

原始日志放 `runs/`（不入库）；**汇总结论必须写进交付 / 审查记录并提交**：被测 SHA、工作区是否有未提交改动、工具版本、实际执行的命令、套件完整性与计数，换一台机器也能核对。

## 8. Git 与工作区

- **主目录 `D:\31days` 只属于用户。** 两个 Agent 都不在主目录写代码。集成时如待合并文件与用户未提交的改动重叠，**立即停止并报告**，不自动 stash、覆盖或还原用户文件。
- **每个 Agent 一个长期工作区**：`worktrees/claude`、`worktrees/codex`。分支命名：实现 `<agent>/<ID>`，审查 `<审查者>/<ID>-review`，规划 `plan/<ID>`。审查一律用 detached HEAD 固定 SHA。
- 提交只用显式文件列表暂存，不用 `git add -A`；提交信息首行带任务 ID。
- 不推送远程、不改全局 Git 配置、不删除对方的分支或工作区。
- `.git` 目前属于 Codex 的沙盒用户。Claude 每次用 `git -c safe.directory=D:/31days` 临时放行，不修改全局配置；是否全局放行由用户自己决定。

## 9. 文档规则

- **Words/ 是“现行规格”。** 修订直接改进正文对应章节，过时表述删除；每份文档末尾保留变更记录表（日期、改了什么、来源）。同一条规则只在一份主文档中完整描述，其他文档只放链接。
- **规格与代码冲突时，报告给用户裁决**，不以“代码已经这样实现”为理由修改规格。
- **game/docs/ 是实施记录。** 测试数量、帧数、存档字段名、场景路径写在这里，不写进 Words/。
- **待决事项集中管理。** Words/ 新增一页待决事项总表。用户裁决后，结论写入对应主文档，总表中保留“已裁决”记录（日期、结论、来源链接），不直接删除。
- 策划文档改写默认由 Claude 实现、Codex 审查，审查重点是改写是否忠实于已确认的规格，并列出与代码的不一致之处。

## 10. ENV-001：协作检查入口

M 级工具任务，Codex 实现、Claude 审查。范围限于环境发现、调用现有检查和生成汇总，不混入游戏修复、依赖安装或自动合并。

- 入口放在 `codexandclaude/tools/`，作为现有验证器的薄包装，不重写 `scripts/verify_game.py` 的判断逻辑。
- 提供明确的模式：环境检查、专项、全量。
- 工具路径按“显式参数 → 本地配置或环境变量 → 自动发现”解析；缺工具时明确报错，不自动安装，不修改全局设置。
- 环境检查覆盖 Godot、Python 及其依赖（如 openpyxl）、Git、Node（表格测试需要）。
- **消除 G3 对 G2 的前置依赖（本任务范围内）。** 现状：`tests/test_game_project.py` 的资源引用检查用正则抓取所有 `res://` 路径，把 `game/tests/test_air_pursuit.gd` 中的输出路径 `res://../outputs/pursuit_air.json` 也当成资源，因此全新工作区未跑 G2 时 G3 必然失败。修法：资源检查跳过指向工程目录外（`res://../`）的运行时输出路径，并补一项测试，证明工程内缺失的资源仍会被报错。允许修改 `tests/test_game_project.py`；不得复制旧结果、创建占位文件或跳过失败测试。修复后，纯文档任务在全新工作区只跑 G3 即可。
- 其余检查仍按真实依赖顺序执行，而不是机械地 G1→G2→G3。
- 输出第 7 节要求的可核对汇总。
- 测试覆盖失败场景：缺工具、路径含空格、子进程失败、超时、缺少汇总行。
